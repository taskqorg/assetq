# Versioned method evaluation

Implements R3-R5/R7-R9 and [task #7](https://github.com/taskqorg/assetq/issues/7), whose original goal is “Let agents and people inspect generation methods, compare candidates and retrieve evidence-backed recommendations from one source.” The complete owner request remains in [intake](intake/2026-11-01-owner-request.md); the task's A1-A7 are the acceptance contract. This is operational evaluation, with no new visual surface.

## Immutable inputs and bounded execution

Owner-authenticated `POST /v1/datasets` and `/v1/evaluators` register `{id, version, document}`. Reusing an identity with different contents fails; an identical retry returns the existing revision and SHA-256. Dataset documents contain `operation` and 1-16 `cases`, each with a unique `id`, `text` and immutable same-project `attachments`. Evaluators contain a nonempty `decision_rule` and `quality_rubric`. Human scores are 0-100 with a judgment and reviewer attribution; absent judgments remain unknown and cannot be synthesized from technical validity.

`POST /v1/comparisons` retains compatibility with historical evidence records. An execution record adds `plan` containing `dataset` and `evaluator` (`id@version`), `constraints`, `repeats` (1-8), `max_jobs` (1-32) and `max_credits`. The operation of every candidate must match the dataset. A fixed case/method/repeat matrix must fit both limits before any jobs are admitted. Snapshot input hashes and the evaluator decision rule with the plan; later revisions never change the plan.

Comparison method pins use the canonical positive decimal version (`method@1`). Reject aliases such as `method@01` and `method@+1` with 422 before retaining a comparison or admitting jobs, including when aliases accompany the canonical candidate. Stored pins must match resolved job identities so reads and resume preserve R5 provenance.

Owner-authenticated `POST /v1/comparisons/{id}/run` admits the fixed matrix through normal durable job admission with deterministic comparison/sample idempotency keys. It is resumable after partial admission, capacity refusal or restart; returned sample IDs remain stable. It runs no provider transport itself. Only explicitly synthetic methods can be launched by this comparison entry point in this initial delivery. Real paid/provider comparison execution remains refused: this task grants no experiment budget or operator binding. A future paid experiment requires its fixed decision rule, freshly reconciled remaining approved ledger budget and existing native executor qualification before effects, not caller-supplied authorization.

`GET /v1/comparisons/{id}` derives technical outcome, verified manifest, reported or unknown credits, elapsed job time, failure rate and missing cases from the original jobs. Technical scores are 1 for a verified successful manifest, 0 for a terminal failure/cancellation, and unknown for unfinished samples; they never score appearance. Repeated reads do not launch work. `POST /v1/comparisons/{id}/scores` appends an immutable human judgment for a completed sample; identical retries are idempotent and changing a judgment requires a new comparison/evaluator record. Retain the observation time, authenticated project grant and caller-provided reviewer attribution. The result is incomplete until every planned job is terminal and every successful sample has a human judgment and known usage. Failed/cancelled samples remain failures, never missing successes. Missing usage is not zero. Results expose the frozen decision rule for owner assessment; they never automatically choose or promote a winner.

## Registry, guidance and control

Existing method creation remains owner-only and append-only, including status edits. `GET /v1/methods` supports `operation`, `capability`, `status` and typed `constraints` filters, bounded by `after` and `limit` (maximum 500). Existing method specifications and job pins remain unchanged. Qualification metadata is a projection of retained real receipt records, bound to the exact method version and specification SHA-256; a different specification has no such qualification. It never enables dispatch or changes method status.

Recommendations remain proposals until an owner explicitly promotes them. Operation is read from the pinned method, and promotion replaces only the same operation/use-case/constraints scope. Reads may specify `operation`; ambiguous multi-operation queries return no qualified method with a reason. Evidence and observation time remain visible even when no route is promoted. Provider health remains separate from qualification and recommendations.

`GET /v1/comparisons?limit=50&after=ID` returns `{items,next}` in stable ID order, including historical evidence-only records. Without pagination parameters it preserves the legacy array response, bounded to 500; use pagination to inspect larger histories. Direct comparison reads also retain historical results and missing cases. Recommendation eligibility is resolved independently of its bounded history page, so newer proposals cannot hide an owner-promoted route.

`GET /v1/status` exposes scoped job counts, reported/unknown usage, bounded per-method outcomes, provider observations, physical storage/capacity, integrity, backup and restore unknowns, and registry/comparison/recommendation revision identifiers. All routes use the existing bearer authority and counted metadata writes. CLI commands are projections of these routes, including `dataset-add`, `evaluator-add`, `comparison-run`, `comparison`, and `comparison-score`; agent callers read the same JSON.

DashQ consumes authenticated summary metadata from `/v1/status` and links to `https://assets.ufobe.com`; the site owns asset and benchmark journeys. ServerQ remains the host-observation owner. Neither integration receives credentials, provider download URLs, direct storage paths or generation authority. No dashboard, host installation, monitoring duplication, paid run or recommendation promotion is part of this delivery.

## Acceptance evidence

Deterministic isolated PostgreSQL fixtures protect immutable revisions, operation separation, fixed repeated samples, partial admission/restart, measured failure/unknown results, human judgments, cross-project refusals and job pins across registry/recommendation changes. Use `python3 scripts/check.py --test registry` during development; R8's full canonical gate covers these fixtures on the frozen candidate. Real image and Meshy qualification are seeded from [native import](evidence/4/native-size-import.md) and [managed delivery](evidence/6/README.md), retaining their exact limits, unknown charges and owner pipeline-only verdict. These receipts authorize no new effects.
